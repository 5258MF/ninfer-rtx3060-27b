# 技术实现与优化说明

[项目首页](../README.md) · [测试结果](benchmarks.md) · [更新记录](../CHANGELOG.md) · [编译与开发](build.md)

本页说明实现方式；按日期发生的修复和发布状态统一放在更新记录中。下文的性能数字对应原有测试，不表示每次更新都会再次获得同等提升。

## Swift 1.5

### 1. 让新引擎在 RTX 30 系上跑

Swift 1.5 的模型格式（GGUF 量化块，IQ2_S / IQ3_XXS 等十几种）只有 ninfer-all 这条新分支能读，它的预编译包只支持 RTX 50 系。移植时：

- 按 sm_86 编译，补齐 cuBLAS 等依赖；
- **精简引擎**（编译开关 `NINFER_SLIM_3060`）：只保留单卡、单路要用的注意力内核，显存和编译时间都省下来；
- **SM 数运行时自动识别**：同一个程序在 3060（28 SM）和更大的卡上都能用，不用重新编译。

### 2. KVMem：12 GB 显存跑 256K 上下文

- 底子是 qzshch/ninfer-kvmem 在新引擎结构上的实现：完整对话放内存（Host KV），显存块表里用"空洞"表示不在显存的页，位置保持原样；
- **Windows 上 Host KV 改用可分页内存**：原来用锁页内存，Windows 上分不出 8 GB；
- 检索按 kv9 的做法完整移植：按消息分段做查询，挑块时对准换行，打分时排除开头、保护块和最近块，CPU 打分矩阵化、多线程；
- 和 MTP 投机解码、看图都兼容。

### 3. 输出留在显存、超窗后只重算新内容

- 单次输出整段预留在显存里，不会被挤出去；开头（系统提示）固定保留；
- 历史超出窗口以后，多轮对话只重算新内容。6 万 token 的对话，接着问每轮从约 140 秒降到 **2–4 秒**；
- 多个对话来回切时，长对话的接续点不会被挤掉。

### 4. 省显存（每一项都换成更大的窗口）

| 改动 | 省下 | 代价 |
|---|---|---|
| 词嵌入放内存（`--embedding-host`） | 约 360 MiB | 无，速度不变 |
| 视觉权重放内存（overlay） | 约 280 MiB | 第一张图约 1.7 秒 |
| MTP 草稿头压成 Q4（用补丁改模型文件） | 约 95 MiB | 无，速度和猜中率在波动范围内 |
| rk4v4 | 32K 上下文省约 260 MiB | 困惑度 +0.10% |

### 5. 提速

- 注意力跳过不在显存的空洞页；
- 页面从内存搬上显卡时批量拷贝（gather），按碎片程度自动选用；
- 精简 MTP 输出头做成可选项（+10.5%）。

### 6. 修 bug

- 长对话里发一条很长的新消息，引擎会崩溃：已修；
- 超窗复用时的几处校验过严、接续点丢失：已修。
- 部分显卡的 SM 数导致实际读入分段变大，KV 容量预算没有同步，引擎启动时报容量曲线越界：修复已合入最新源码。

### 7. 启动器

- 按启动时的空闲显存自动算窗口，整卡留约 150–200 MiB；估多了引擎会报真实可用量，启动器自动缩小窗口重试；
- 单次输出可以选"自动"，按窗口大小分配；
- 先显示上次配置，回车直接启动；按 C 一步步重新选，每一步都写着推荐值和上限。

### 当前源码中的构建支持

| 改动 | 内容 |
|---|---|
| KVMem | 移植 qzshch/ninfer-kvmem 的空洞块表、设备放置事务、稀疏工作集、滚动预填窗口、解码环形窗口和检索机制 |
| 3060 精简 | `NINFER_SLIM_3060` 保留单卡、单路、H24 注意力和 int8 / rk8v4 / rk4v4 内核 |
| 内存和显存 | Windows Host KV 用可分页内存；词嵌入放锁页内存；开头和输出按环境变量预留 |
| kv9 检索 | 按消息分段查询、对准换行、排除开头/保护块/最近块、CPU 打分矩阵化多线程；默认查询行数 1024 |
| 长对话复用 | 修复工作集恢复、长追问的 KV 覆盖范围和接续点问题 |
| 注意力和换入 | 跳过空洞页；页面换入按碎片程度自动选批量 gather |
| SM 自适应 | GDN 路线表运行时按真实 SM 数选择；rope 容量 = 6 × SM |
| 首次显卡校准 | 精简版只校准实际编译的 int8 / rk8v4 / rk4v4，跳过未编译的 E8 内核，避免未知显卡首次启动失败 |
| 启动容量 | KVMem 自动容量使用规划器曲线下限，修复实际读入分段经 SM 对齐后变大造成的启动容量越界 |

## Bonsai2 12G

### 1. 让引擎能在 RTX 30 系上跑

原版引擎只支持 RTX 40/50 系（sm_89 / sm_120），在 3060 上编译不过、跑不起来。移植时改了这些：
- 编译配置里放行 sm_86；
- 3060 只有 28 个计算单元（SM），而原版按 82 个设计，改掉后才不会一启动就报错；
- 3060 不支持 FP8 指令，把这条路径关掉；
- 修了一个评测工具里的内存分配错误。

### 2. 生成速度优化（+27~30%）

- **单 token 生成改走 Tensor Core**：原来用的是逐行的普通计算。
- **2-bit 权重改成在寄存器里直接解码**：原来要查一张放在共享内存里的表，访问冲突严重，带宽卡在理论值的一半左右。改完带宽提升 20–50%，输出逐位一致。
- **只搬实际需要的数据行**：每个计算单元能同时多跑一两组任务，又快了 3–14%。

### 3. 读入速度优化（+40%）

- **自己写了一个新的 int8 计算核心**（提升最大的一项）：
  - 权重在寄存器里解码，省掉一轮来回搬运；
  - 计算块加大到 32×64；
  - 三级流水线；
  - 按显卡二级缓存（L2）的大小分组调度，让权重和输入尽量留在缓存里；
  - 输出先在共享内存里整理，再合并写回显存。

  效果：矩阵计算从 45 TOPS 提到 61 TOPS，整体读入快了 26–27%，**输出逐位一致**。
- **输入量化改成向量化读写**：从 40.7 ms 降到 22.8 ms，已经接近显存带宽的极限。
- **任务网格化**：让 28 个计算单元都有活干。
- **重新标定切换阈值**：实测 3060 上的最佳切换点是 17 个 token，和引擎作者在另一张卡上的结论一致。

一些方案经测试没有收益，未纳入当时的发布构建。

### 4. 修 bug

- **多轮对话必崩（原版引擎的已知缺陷）**：续写时有一个长度校验写错了，第二轮就报错，而且会让整个引擎不可用。现在修好了。
- 做 KVMem 过程中又修了几个缓存管理的问题，比如"重新生成"或改最后一条消息时引擎挂掉、闲置缓存清出后再复用报错、接近上限的长提示报错。现在四种模式都经过了长文、多轮、工具循环、看图的回归测试。

### 5. KVMem：12 GB 显存跑 256K 上下文

参考 kvmem-llama.cpp 的做法和官方推荐参数，移植到这个引擎上：
- **显存里只放活动窗口**：开头 8K 的系统提示和工具定义，加上按当前问题挑出的历史，以及回答预留空间；窗口大小取决于模式和配置，见[12G 使用指南](bonsai2-12gb.md)；
- **其余历史放在普通内存里**：256K 大约要 8.4 GiB，用的是普通可换页内存，不锁页，没有锁页内存不够用的问题；
- **和投机解码（MTP）兼容**：最早的版本开 KVMem 必须关 MTP，速度从 53 掉到 30。现在 KVMem 下真实对话仍有 **48–50 token/秒**。

之后又对照 KVMem 的论文迭代了几版：
- 挑历史时用**用户真正的问题**，不只用工具返回的结果。以前在 8.9 万 token 的工具结果场景里会答错，现在答对了；
- 本轮新输入的内容一定保留在显存里；
- 历史被挤出显存后，按新挑出来的内容把本轮输入重新算一遍，和论文的做法一致。

### 6. rk8v4：更省显存的 KV 格式

- 对话记录（KV）里，K 部分用 int8，V 部分用 4-bit，每个 token 只占 int8 格式的 77%；
- 同样的显存，上下文多放约 30%（普通 88K → rk8v4 112K）；
- 代价是 PPL 增加约 0.1%，短对话时生成慢约 5%；
- 8.6 万 token 的藏句测试 3 次全对。

### 7. 视觉权重和词嵌入放内存

- 看图功能本来要常驻约 300 MiB 显存。现在平时放在内存里，来图时分 30 段依次搬上显卡计算，每张图多约 0.1 秒。
- 词嵌入表（把文字变成向量的那张表）占 322 MiB。现在也放在内存里，每步只读用到的那几行，显卡直接从内存读。
- 两项合计省下约 600 MiB 显存，每种模式的上限都高了 2～4 档。读入和生成速度不变，看图结果和原来逐字一致。
- 2026-10-01 的 12G 发布版未采用 8G 方案中的“MTP 压成 4-bit”和“读入分段 512”，对应当时的测试结果：
  - MTP 压成 4-bit：猜中率从 0.679 降到 0.655，生成慢约 3%；
  - 读入分段 512：当时读入慢约 2%，省的显存不够多开一档；2026-10-03 的本机第十轮构建按本轮目标统一使用 512。

### 第十轮本机构建

2026-10-03 加入 SM 数量自适应、按空闲显存分配 KVMem 窗口与输出、512 分段和查询、换行边界截取、保留区域排除和批量 gather，并修正手动 64K 输出的容量计算。这些更新尚未上传到当前 12G 网盘包；验证范围见[测试结果](benchmarks.md#bonsai2-12g-第十轮补充验证)。

## Bonsai2 8G

12G 版已有的移植、速度优化、修 bug、KVMem、rk8v4、视觉权重放内存，8G 版都保留了，详见[12G 技术说明](#bonsai2-12g)。为了塞进 8 GB，又做了下面这些：

### 1. 换成 ptq1 模型

- 12G 版用的是 PQ2 格式（文件 7.7 GiB），8G 版换成更小的 **ptq1**（约 1.6 位，文件 6.6 GiB），文件小约 1.1 GiB，显存里的权重也相应变小。
- 3060 8GB 同样有 28 个计算单元，所以不用给它单独编译引擎。
- 我们没做 ptq1 和 PQ2 的回答质量对比。

### 2. 猜词模块（MTP）压成 Q4

- **MTP 必须留着**：关掉 MTP 只省 478 MiB，生成速度却从 45 掉到 11–12 token/秒。原因是 ptq1 一次生成一个 token 走的是没优化过的慢路径，有了 MTP 就能一次验证 4 个 token。
- 原版 MTP 是 8 位。我把其中 5 个矩阵重新量化成 4 位（Q4），**省约 210 MiB**；生成速度不变（45.2–45.6 token/秒），猜词命中率还从 62.5% 略升到 64.1%。
- MTP 只负责"猜"，每个词最后都要由主模型验证，所以它的误差**只影响猜中率，不影响回答内容**。
- 引擎改了 3 处，让它能读 Q4 格式的 MTP，原版模型的行为不变。

### 3. 词嵌入放内存

- 词嵌入就是"token 编号 → 向量"的查表，共 265 MiB。每生成一个 token 只查 1 行（约 1 KB），所以放在内存里、让显卡通过 PCIe 直接读。
- 实测速度一样（45.3 对 45.2–46.4 token/秒），猜中率完全相同。

### 4. 其他省显存的设置

- **视觉权重放内存**（和 12G 版一样）：省约 260 MiB，每张图多约 0.1 秒；
- **读入分段从 1024 改成 512**：临时缓冲区省 85 MiB，读入速度基本不变；
- **关掉额外的缓存槽**：一次只服务一个对话，用不上。

### 5. rk4v4 也能开 KVMem

- 原版引擎里 rk4v4 不让开 KVMem。查了源码，确认相关代码不区分 KV 格式，于是只放开了这个检查，没动计算代码。
- 结果：rk4v4 下显存里能放 64K（rk8v4 是 44K），所以回答空间给到 32K，历史还有 32K。26 万 token 藏句测试答对，一次写满 32K 回答也正常。
- rk8v4 和 rk4v4 的计算代码同名，没法编进同一个程序，所以包里有两个引擎程序，放在同一个文件夹，启动器按模式自动选。

### 6. 懒人包里现场转换模型

- 魔搭社区上只有原版 ptq1 模型，MTP 是 8 位的。在用户电脑上用 Python 转换得装一堆东西，所以改成打补丁。
- 补丁的原理：ptq1 原文件和 Q4 版只有 5 个 MTP 矩阵不同。补丁里记着"哪些段从原文件复制、哪些段换成新数据"，新数据只有 226 MB。
- 转换用纯 PowerShell 完成，十几秒。转完校验 SHA256，和我这边生成的文件逐字节一致后，才删掉原始文件。

### 显存账（ptq1 + Q4 MTP，视觉和词嵌入都放内存）

| 项 | 大小 |
|---|---|
| 权重 | 5.47 GiB |
| 当前对话的循环状态（48 层线性注意力） | 约 147 MiB |
| 其余临时缓冲区 | 约 205 MiB |
| KV，每 1024 token | rk8v4 27.7 MiB，rk4v4 18 MiB |
| 视觉放内存后留在显存的部分 | 约 68 MiB |
| KVMem 额外 | 约 240 MiB |

再往下省基本到头了。还能动的几项，比如输出层放内存、MTP 压到 3 位，要么会让速度掉一半，要么省得太少。
