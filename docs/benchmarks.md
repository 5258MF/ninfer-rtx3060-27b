# 测试结果与已知限制

[项目首页](../README.md) · [更新记录](../CHANGELOG.md)

这里按版本保存已有测量和验证范围。不同工具、模型格式、提示词和输出长度的速度不能直接横向比较；文档整理没有重新测量这些历史结果。256K 是可配置的总上下文，KVMem 每轮只读入选中的历史，不能据此保证所有内容都能精确召回。

## Swift 1.5

### 质量（困惑度，越低越好）

同一台机器、同一个测试工具（引擎自带的 `ninfer-perplexity`，语料 `perplexity-1m`，上下文 4096）：

| 领域 | 12G 版 Swift-Bonsai-2 | **Swift 1.5 IQ2_S** |
|---|---|---|
| 中文维基 | 7.894 | **5.443** |
| 英文长文 PG-19 | 8.656 | **7.439** |
| 英文 WikiText | 7.827 | **6.321** |
| 代码 | 1.860 | **1.716** |
| **总体** | 5.628 | **4.587**（低 18.5%） |

### 速度（RTX 3060 12GB）

| 指标 | 数值 |
|---|---|
| 生成速度（引擎自带 refbench，MTP 投机解码） | **约 43–45 token/秒** |
| 生成速度，MTP 输出头选"精简" | **约 47 token/秒**（+10.5%） |
| 读入速度（4K / 24K 上下文） | 514 / 453 token/秒 |
| 19 万 token 第一次读入 | 约 9 分钟 |
| 25 万 token 第一次读入 | 约 12 分钟（约 365 token/秒） |
| 长对话接着问（19 万 token 之后） | 每轮约 **1.3–1.4 秒**开始回答 |

- 和 12G 版用同一个工具（refbench、32K、都用 rk8v4）对比过：短回答生成慢约 8%，长上下文慢约 20%，读入慢约 35%（2-bit 权重计算量更大）。之后默认换成 rk4v4，生成又快了 14–22%。换来的是质量明显更好、上下文更长。
- 12G 版介绍里的"约 53 token/秒"是用另一个工具（`ninfer_bench`）测的，和这里的数字不能直接比。
- 速度测试都是开关交替测几轮，排除显卡发热降频的影响。

### 长上下文

| 场景 | 结果 |
|---|---|
| 12 万 token 长文藏一句话 | **找到**；多轮追问、切到别的对话再切回都正常 |
| 19 万 token 长文藏句、工具调用、多轮复用 | 单次输出 16K 时 5 次全部通过；输出调到 23K（检索区变小）时，工具那一项没过 |
| 25 万 token 长文藏一句话 | **没找到**：暗号所在的那一块没被挑进显存（见本页的已知限制） |
| 6 万 token 对话，超出显存窗口以后接着问 | 每轮 2–4 秒（改之前每轮约 140 秒） |

### 测试环境

| 项 | 配置 |
|---|---|
| 显卡 | RTX 3060 12GB（28 SM，显存带宽 360 GB/s） |
| CPU | Ryzen 7 3700X |
| 内存 | 32 GB（Host KV：200K 上下文预留 8 GB，256K 预留 10 GB） |
| 系统 | Windows 11 |
| 前端 | DeepSeek Harness 桌面版（其他 OpenAI 兼容客户端也能用） |

### 已知限制

- **25 万 token 藏句没找到**：按块打分时，暗号所在那一块得分偏低，没被挑进显存。需要精确查找时，材料尽量控制在 12–19 万以内；贴很长的材料时，先发材料，再单独发一条问题，召回会好很多。
- **第一次读入慢**：19 万约 9 分钟，25 万约 12 分钟。之后接着问很快。
- **一次只处理一个请求**：同时发多个会排队。
- **单次输出（含思考）有上限**：自动时 3060 上约 23–28K，超过会被截断，写很长的东西要分几步。
- **显存大于 12 GB 的卡**：窗口有上限，多出来的显存暂时用不上。
- **只支持 RTX 30 / 40 系**：引擎按 sm_86 编译。RTX 50 系请用 Ryan-gsq 分支的官方预编译包。

### 测试方法

- 速度用引擎项目自带的 refbench，困惑度用 `ninfer-perplexity`。开关交替测，排除显卡过热降频的影响。
- 长上下文用藏句找回、多轮追问、工具调用、切对话再切回测试，每次改动后都回归。
- 懒人包实测过下载（含断点续传）、校验、补丁转换、真机启动和 `测试.bat`。

## Bonsai2 12G

以下为 2026-10-01 及此前优化的记录，表中的“现在”对应这一发布构建。2026-10-03 第十轮结果另见[补充验证](#bonsai2-12g-第十轮补充验证)。

### 速度

| 指标 | 刚部署时 | 现在 | 提升 |
|---|---|---|---|
| 实际对话生成速度（中文、英文、代码、思考 4 类平均） | 40.6 token/秒 | **52.8 token/秒** | **约 +30%** |
| 读入长文速度（2048 token 一段） | 694 token/秒 | **965 token/秒** | **+40%** |
| 短提示读入（32 token） | 218 token/秒 | **385–393 token/秒** | 约 +80% |
| 不开投机解码时的纯生成速度 | 19.6 token/秒 | **30.6–30.9 token/秒** | 约 +57% |

- 4 类内容分别是：中文 46.2、英文 50.8、代码 67.0、思考 63.1 token/秒。
- 让模型照抄一段代码或数据时，猜词命中率超过 90%，速度能到 **80–100 token/秒**。上面表格里没用这种数，按正常对话算。
- 所有数字都是同一台机器、同一个程序，打开和关闭优化交替测 3 轮，每轮之间等显卡降温，尽量排除发热降频的干扰。

### 长上下文

| 场景 | 结果 |
|---|---|
| 26 万 token 长文里藏一句话，再让它找出来 | **答对**；追问也答对，追问只要约 5 秒就开始回答 |
| 26 万 token 第一次读入 | 约 12 分钟（约 370 token/秒）；读完后生成速度仍有 51.5 token/秒 |
| 8.9 万 token 长文第一次读入 | 约 3 分钟（约 450 token/秒） |
| 6.4 万 token 文档多轮追问、追加内容再问旧内容 | 4 轮全对 |

### 正确性

- 速度优化里，**除一项以外，输出和原版逐位一致**。
- 那一项是把"什么时候切换到 int8 算法"的阈值从 33 调到 17，困惑度（PPL）只变了 +0.033%，在引擎作者给的允许范围内。
- 视觉权重放内存这个功能，看图结果和原来**逐字一致**（6 轮 18 次测试）。

### 测试环境

| 项 | 配置 |
|---|---|
| 显卡 | RTX 3060 12GB（28 SM，显存带宽 360 GB/s） |
| 内存 | 32 GB 推荐（KVMem 长对话要占约 10 GB）；16 GB 只能用普通模式 |
| 系统 | Windows 11 |
| 前端 | DeepSeek Harness 桌面版（其他 OpenAI 兼容客户端也能用） |

其他 sm_86 显卡（3060 Ti / 3070 / 3080 / 3090）用同一套源码改动就能跑，但要按实际 SM 数重新编译，各项上限也要重新测。

上面的 SM 编译说明属于已发布的 2026-10-01 版本；第十轮本机构建的变化见更新记录。

### 已知限制

- **只支持 RTX 30 系**：懒人包里的程序是专门给 sm_86 编译的，40/50 系请用原版引擎。
- **一次只处理一个请求**：同时发多个会排队。
- **KVMem 两种模式下一次回答（含思考）默认最多 32K**：超过会被截断，写长东西要分几步。可以调大，KVMem 最多 40K，KVMem + rk8v4 最多 64K（调大回答空间不会缩小检索窗口）。
- **KVMem 每轮只能看到挑出来的部分历史**：超长对话里，偶尔可能漏掉没被挑中的细节。需要模型看到全部内容时，用 rk8v4 模式（112K 以内）。
- **26 万 token 第一次读入要十几分钟**：之后接着问就很快。
- **显存余量不大**：上限是按"显示器接在这张卡上、桌面占约 1.3 GB"算的，开到上限时整卡只剩约 200 MiB。同时开着游戏、视频或浏览器硬件加速，可能变慢或起不来，这时往下调一档（4K）。显示器接在核显上就宽裕得多。

### 测试方法

- 速度测试用引擎项目自带的 `ninfer_bench`，以及真实对话的 A/B 测试脚本（中文、英文、代码、思考 4 类，采样开启）。打开和关闭优化交替测，每轮之前等显卡降到 60–65°C。
- 正确性用逐位对比输出和 PPL 门限检查，长上下文用藏句找回、多轮追问、工具循环测试。
- 每项改动都有环境变量开关，可以随时关掉，退回原版的做法。

## Bonsai2 8G

### 速度

| 指标 | 结果 |
|---|---|
| 生成速度（`ninfer_bench`） | **约 45 token/秒**（rk4v4 约 38） |
| 真实对话回答（中位数） | **约 36–40 token/秒** |
| 短问题（懒人包自带的 `测试.bat`） | 38–46 token/秒 |
| 读入长文（2048 token 一段） | 约 620 token/秒 |
| 长时间生成、显卡 89°C 降频时 | 约 24 token/秒 |

- 比 12G 版慢约 30%（`ninfer_bench` 45 对 67）。慢的原因几乎全在 ptq1 模型本身：已有速度优化大多针对 12G 版的 PQ2 格式。[8G 省显存改动](implementation.md#bonsai2-8g)基本不影响速度。
- 所有数字都是在 **3060 12GB** 上限制显存测的：只看引擎自己占多少显存，保证不超过 7.5 GB。**没在真的 8GB 卡上测过**，真卡的速度见本页的已知限制。

### 长上下文

| 场景 | 结果 |
|---|---|
| 26 万 token 长文里藏一句话，提问时不给提示，让它找出来 | KVMem 模式和 KVMem + rk4v4 模式都**答对** |
| 一次回答写满上限（KVMem + rk4v4，32K） | 写满 32,768 token 正常结束，引擎显存不涨 |
| 26 万 token 第一次读入 | 约 12.5–14 分钟（300–340 token/秒，越往后越慢） |
| 5.7 万 token 长文全部放在显存（普通模式） | 2 次都找对 |
| 6.4 万 token 长文（KVMem 模式、普通 rk4v4 模式） | 正常 |

### 显存（引擎自己的占用，用 nvidia-smi 量，取测试过程中的最高值）

| 模式 | 引擎最高占用 |
|---|---|
| 普通 | 7628 MiB |
| KVMem（默认 44K 档） | 7659 MiB |
| KVMem（48K 档） | 7760 MiB |
| 普通 rk4v4 | 7627 MiB |
| KVMem + rk4v4 | 7617 MiB（一次写满 32K 回答后也是 7617） |

每个模式都过了同一套测试：文字、看图、工具调用、多轮对话、8K 藏句找回。

### 测试环境

| 项 | 配置 |
|---|---|
| 显卡 | RTX 3060 8GB（28 SM）；实际测试用的是 3060 12GB，限制引擎只用 7.5 GB |
| 内存 | 32 GB 推荐（KVMem 256K 长对话的历史要占约 7–8 GB，另有约 1 GB 锁页内存给词嵌入和视觉）；16 GB 建议只用普通模式 |
| 硬盘 | 转换时临时要约 14 GB，转完占约 7.3 GB |
| 系统 | Windows 10 / 11 |
| 前端 | DeepSeek Harness 桌面版（其他 OpenAI 兼容客户端也能用） |

### 已知限制

- **没在真的 8GB 卡上测过**：所有结果都是在 3060 12GB 上、按"引擎自己不超过 7.5 GB"测出来的。
  - 3060 8GB 的显存带宽是 240 GB/s，12GB 版是 360 GB/s，所以真卡上生成速度大概率比上面的数字低，具体多少没测。
  - 显示器插在这张显卡上时，Windows 桌面、浏览器等程序也要占显存。8 GB 减去引擎的 7.5 GB，只剩约 0.5 GB。如果启动失败或者特别慢，就在向导里把上下文调小一档，或者关掉占显存的程序（浏览器硬件加速、游戏等）。
  - 能用核显出画面的话（显示器插主板），独显几乎都能留给模型，也可以选 KVMem 的 48K 档。
- **只支持 RTX 30 系**：包里的程序是专门给 sm_86 编译的。
- **比 12G 版慢约 30%**，原因是 ptq1 模型本身慢。
- **一次只处理一个请求**：同时发多个会排队。
- **KVMem 模式下一次回答（含思考）最多 16K**：超过会被截断，写长东西要分几步。普通模式和 KVMem + rk4v4 模式是 32K。
- **KVMem 每轮只能看到挑出来的部分历史**：显存里放 28K 历史（KVMem + rk4v4 是 32K），比 12G 版少。超长对话里，偶尔可能漏掉没被挑中的细节。需要模型看到全部内容时，用普通模式（56K 以内）。
- **26 万 token 第一次读入要十几分钟**：之后接着问就快了。

### 测试方法

- 速度用引擎项目自带的 `ninfer_bench`，开关某项改动交替测 3 轮。
- 显存的测法：先记下"开引擎前"的显存占用，开引擎后跑完全套测试，取过程中的最高值，两者相减就是引擎自己的占用。每个模式的上限都按"不超过 7680 MiB"一档一档试出来，测试时按 7650 卡线，留 30 MiB 误差。
- 每档都要通过：基本问答、看图、工具调用、多轮对话、项目自带的 8K 藏句找回。KVMem 模式再加 26 万 token 藏句测试。项目自带的 256K 样例在提问里就带着答案，所以换成了新的藏句内容，提问时不给提示，回答里两个值都对才算通过。
- 懒人包另外测了：向导的 9 种选法、模型转换和校验、下载和校验，以及每个引擎程序都真机启动一次，跑 `测试.bat`。

## Bonsai2 12G 第十轮补充验证

2026-10-03 的本机新构建尚待发布。这批结果与上面的历史基准分别记录：

- 固定三个提示词，temperature=0，每次输出 256 token，old / new / new / old 交替运行：旧版 54.370、新版 54.437 token/s，三个提示词的输出 hash 均相同；没有明显提速证据。
- 快速困惑度共 261167 个计分 token，新旧总体和各领域报告相同，总体 PPL 为 5.6284340215296345。
- 100K、七轮长对话在旧版、新特性关闭、512 查询、512 查询关闭 gather、1024 查询五种配置中均通过。
- 四种启动模式、看图和工具往返通过；gather 的独立逐字节校验通过。
- 完整旧 KV 单测仍有 3 项预留/驻留语义断言失败，相关预留函数与本轮前相同；未把完整单测列为通过。
- 自动缩窗重试的正例使用模拟容量报告；真实显存压力测试未触发同一报错，部分尝试遇到主机锁页分配失败。
- 普通 88K、rk8v4 112K、KVMem 总上下文 256K 的配置上限沿用之前结果，本轮没有证明显存容量或回答质量提升。
