# Bonsai2 8G 版

**简体中文 | [English](README-8GB.en.md)**

面向 RTX 30 系 8GB 显卡的 Windows 推理方案，使用 Swift-Bonsai-2 27B ptq1 模型，模型下载约 6.6 GiB，MTP 草稿头转换为 Q4。

**测试使用 RTX 3060 12GB，并限制引擎显存占用；没有在真实 8GB 显卡上验证。** 实际 8GB 显卡的速度和桌面显存余量可能不同，详见[测试范围与限制](#测试结果与已知限制)。

## 下载与开始

下载 `ninfer-3060-8g-bonsai2-oneclick-0.1.3.zip`，共用网盘链接和提取码见[项目首页](README.md#下载)。

需要 Windows 10 / 11、支持 CUDA 13 的 NVIDIA 驱动，内存建议 32 GB，第一次转换需约 15 GB 空闲磁盘。完整解压后双击 `启动.bat`，第一次会下载并转换模型；出现 `listening` 后运行 `测试.bat`。

## 启动与客户端

完整解压后运行 `启动.bat`；回车使用当前配置，按 C 打开向导。首次使用会下载模型，8G 版还会转换 MTP。出现 `listening` 后运行 `测试.bat`。客户端按生成的 `接入信息.txt` 填写。

默认 Base URL 是 `http://127.0.0.1:8084/v1`，模型 ID 是 `qwen3.8-27b`。上下文和输出上限必须与启动配置一致。

## 模式与容量

### CPU 检索与显存窗口（0.1.2）

KVMem 默认把 FP32 检索索引和 BF16 查询暂存放到锁页内存，CPU 用 AVX2/FMA 分块计算；不降低索引精度，总上下文仍可配置 256K。256K 下约 256.25 MiB 索引加 144 MiB 查询暂存移出显存，主机内存占用相应增加。

### 按实际提示词分配 KVMem 窗口

**当前 main 源码（2026-10-06）：** 自动 KVMem 模式只确定驻留预算，有限的 API 申请上界随驻留容量变化；不再提前按固定 SYS、固定 36K／平分或 32K 输出封顶划分。引擎按实际 system/developer/工具前缀逐请求分配检索与输出。本引擎的 `--default-max-tokens` 也会限制显式请求，并非只在客户端不传参数时生效。旧 SYS/sink 配置或初始化种子不等于真实前缀。客户端压缩策略由客户端自行配置，包内不附 DSH 测试启动项。

本轮 main 启动器支持三种驻留选择：`recommended` 取历史推荐与当前允许上限的较小值，`auto` 取当前允许上限，也可手动填写范围内的 token 数。推荐值不是硬上限；读不到显存或配置越界时拒绝启动。按 C 先选 KV／输出头／Graph，再选驻留、逻辑上下文和 API 上限；菜单支持数字选项，启动前会重新检查显存。8G 始终按整卡 8GiB 扣除桌面与其他占用。校准范围与短测结果见[更新记录](CHANGELOG.md#2026-10-06bat-菜单与显存容量校准main)。


启动时先按空闲显存确定总驻留容量 C；每次请求再准确计算系统提示、developer 指令和工具定义的完整开头 S。检索不包含 S，输出使用剩余容量。

| 总上下文 | 检索推荐范围 | 优先目标 | 输出预留 |
|---|---|---|---|
| 256K | 32K–36K | 36K | C − S − 检索，至少 8K |
| 128K | 16K–18K | 18K | C − S − 检索，至少 8K |
| 200K | 25K–28.125K | 28.125K | 同上 |

开头按完整渲染后的 token 数计算，Bonsai 按 64 token、Swift 按 128 token 对齐。不再固定预留 8K 开头，也不再把 KVMem 输出限制为 16K/32K。容量不足时先缩检索，低于推荐范围会提示；完整开头和 8K 输出都放不下时返回容量错误。实际生成仍受客户端请求长度、剩余总上下文、停止词以及模型结束影响；8K 是显存预留，不保证每次生成 8K。

Harness 在第一次请求前即可配置：`contextWindow` 填总上下文，`maxTokens` 使用启动器生成的数字。这是最短开头情况下的申请上限，实际请求的开头更长时，引擎会自动降低本轮输出预算。启动缩窗后重新生成接入信息；本机启动器在允许同步时同步 dsh。旧的手动 OUT/ANSWER、SYS/SINK 和 WINDOW 会迁移到自动分配。

8G 在 12GB 测试卡上也先扣除当前桌面/驱动占用，再按 8GB 预算计算。20K 是小容量测试或低空闲显存下的容量，67K 是假设整块 8GB 空闲时的理想预算；二者不能作为同一台电脑的固定上限。较小窗口可以运行，但超长历史召回可能变差。

同容量对照在 RTX 3060 12GB 上测得：8G rk8v4 少约 **404 MiB**、8G rk4v4 少约 **402 MiB**、12G rk8v4 少约 **401 MiB**。整卡采样减启动前占用，包含桌面波动，不能视作逐进程精确计量。四个短请求的输出在 CPU/GPU 路径中一致；生成速度基本持平，短提示词读入增加约 13–16 ms。

0.1.2 历史扩容实测点（**不是当前分配默认值**）：8G rk8v4 56K = 40K 历史 + 16K 回答；8G rk4v4 84K = 52K + 32K；12G rk8v4 112K = 80K + 32K。12G 25.2 万 token 的三处藏针和两轮续问通过；8G 超长召回对照见[更新记录](CHANGELOG.md#012---2026-10-04)。本轮未重测完整 16K/32K 长输出或困惑度，也未在真实 8GB 卡验收。

排查时可设置 `NINFER_TERNARY_KVMEM_CPU_RETRIEVAL=0` 回到 GPU 索引/打分，启动器同步采用相应显存预算。普通模式没有这项索引迁移收益。



和 12G 版一样有四种模式。启动时有向导，每一步都标了推荐值和上限。

| 模式 | 最长上下文 | 一次回答最多 | 适合 |
|---|---|---|---|
| **普通**（推荐） | 56K（全部在显存） | 32K | 最稳，日常对话，模型能直接看到全部内容 |
| **KVMem**（推荐，默认） | **256K** | 自动，至少预留 8K | 长文档、长对话、写代码的工具循环 |
| 普通 rk4v4（不推荐） | 84K（全部在显存） | 32K | 超过 56K、又希望模型看到全部内容时 |
| KVMem + rk4v4（当前测试配置） | **128K** | 自动，至少预留 8K | 显存更省，速度与精度代价见历史测试 |

- 两种 KV 格式都比 12G 版用的 int8 更省显存：
  - **rk8v4**：K 用 int8、V 用 4 位，前两种模式用它；
  - **rk4v4**：K 和 V 都用 4 位，同样的显存能放更多内容。旧构建曾测得速度与 PPL 代价；当前 128K KVMem 配置采用 rk4v4／关闭 Graph，速度以本页新表为准，不把旧百分比视作固定代价。
- **旧版 KVMem 显存里放多少**：

| 模式 | 显存里的 KV | = 挑出来的历史 + 回答空间 |
|---|---|---|
| KVMem（旧版默认档） | 44K | 28K + 16K |
| KVMem（旧版 48K 档） | 48K | 32K + 16K |
| KVMem + rk4v4 | 64K | 32K + 32K |

- **旧版 48K 档要选了才会用**，适合显示器接在主板上（用 CPU 核显出画面）的情况。它让引擎占到约 7.6 GiB（7760 MiB），只给桌面留约 430 MiB；显示器插在这张显卡上的话不够用。

## 模型准备与参数调整

整体和 12G 版一样：

- **解压后约 0.9 GB**，模型不在包里。第一次启动时自动从魔搭社区下载 `bonsai2_27b_swift_ptq1.ninfer`（6.6 GiB，国内直连）。支持断点续传，中途关掉窗口下次会接着下。下完自动校验，然后转换成 8G 用的版本。也可以自己用浏览器下载，放进 `model` 文件夹。
- **不用配环境**：只要装 NVIDIA 显卡驱动 580 以上。不用装 CUDA、Python，也不用装 VC++ 运行库。
- **双击 `启动.bat`**：先显示上次的配置，回车直接启动；按 C 一步步重新选，依次是 KVMem、KV 格式、显存档（只有 KVMem 模式有）、看图、上下文、思考长度（开头与输出自动分配）。每一步都写着推荐值和上限，输入超过上限会让你重输。
- **启动后自动生成 `接入信息.txt`**：写着客户端该怎么填，包括接口地址、模型名、上下文窗口、最大输出，还有一份 DeepSeek Harness 可以直接用的配置。
- 支持 OpenAI、Anthropic Messages、OpenAI Responses 三种接口格式，支持工具调用和看图。
- 只有一个模型：Swift-Bonsai-2（ptq1 + Q4 MTP）。12G 版里的"原版 Bonsai-2"没放进来。
- 在 12 GB 显卡上运行会提示"可以用 12G 版"，但不拦着。

完整测试范围见[测试结果与已知限制](#测试结果与已知限制)，内部改动见[技术实现](#技术实现)。

## 测试结果与已知限制

### dsh 标准／精简模式实测

使用 dsh 0.2.0-rc.2 自带的 standard / minimal 预设、隔离配置和本地模型。测试入口显式通过原生预设注册器绑定模式；原生 headless 入口本身不会绑定桌面预设。任务为读入两个数字、写入和、再读回核对，每种模式均完成三次工具往返。没有使用用户私人系统提示或凭据。

| Bonsai 测试配置 | 模式 | 完整开头（对齐后） | 检索 | 输出预留 | 结果 |
|---|---|---:|---:|---:|---|
| 12G，256K 总长／80K 驻留 | standard，26 工具 | 6528 | 36864 | 38528 | 正确写入并核对 42 |
| 同上 | minimal，1 工具 | 448 | 36864 | 44608 | 正确写入并核对 42 |
| 8G 方案，256K 总长／20K 驻留 | standard | 6528 | 5760 | 8192 | 正确写入并核对 42 |
| 同上 | minimal | 448 | 11840 | 8192 | 正确写入并核对 42 |

12G 同容量旧配置两种模式都预留 32768 输出；新配置分别增加 5760 / 11840 token。短任务耗时新／旧约 12.969／12.937 秒和 9.312／9.313 秒，没有测出提速。此轮确认的是分配余量，不是新的显存节省；此前 CPU 索引迁移约 400 MiB 的收益属于 0.1.2。8G 的 11K 系统提示配 30K 重复正文、仅 1K 检索的另一项测试未答对标记，不能把小窗口可用等同于超长召回可靠。没有真实 8GB 硬件、完整最大长度生成或新困惑度测试。


这里按版本保存已有测量和验证范围。速度数据不能直接横向比较，除非测试工具和模型格式相同，提示词与输出长度也一致；文档整理没有重新测量这些历史结果。256K 是可配置的总上下文，KVMem 每轮只读入选中的历史，不能据此保证所有内容都能精确召回。

### 速度

2026-10-05，RTX 3060 12GB / Windows；完整输出头、MTP draft3、CPU 看图、prefill chunk512。文本/代码输入分别为 56/49 token，输出 256 token；每组预热 1 次、正式 3 次。生成速度是引擎 decode 中位数（token/s），不是端到端吞吐。

| 配置 | Graph | 测试驻留窗口 | 文本生成 | 代码生成 |
|---|---|---:|---:|---:|
| Bonsai2 8G · rk4v4 | 关 | 48K | 32.26 | 31.03 |

无缓存预填充：实际输入为 2K / 8K / 16K，每档预热 1 次、正式 3 次，最多生成 8 token。下表是 prefill 中位速度，首 token 延迟（TTFT）单列；引擎计时和 usage 输入计数一致，缓存命中为 0。

| 配置 | Graph | 2K 预填充 | 8K 预填充 | 16K 预填充 | 16K TTFT（秒） |
|---|---|---:|---:|---:|---:|
| Bonsai2 8G · rk4v4 | 关 | 558.43 | 557.65 | 533.90 | 30.71 |

10 个配置共计 90 个正式 prefill 样本、30 个预热样本。不同模型驻留量不同；同模型/KV 的 Graph 对照使用相同窗口，小幅差异不构成普遍提速保证。输入均未超出驻留窗口，不代表超长历史换页速度。表中 IQ3 37K、Bonsai8 48K 是当时测试窗口，当前推荐档为 IQ3 33K、Bonsai8 36K，均不是硬上限；auto 和手动驻留受实时显存及匹配组合的校准边界限制。IQ3 首次因余量 223.68 MiB 触发旧 300 MiB 规则，重试完成，异常记录保留。[原始指标与方法](benchmarks/20261005/README.md)。

### 已知限制

- **没在真的 8GB 卡上测过**：所有结果都是在 3060 12GB 上、按"引擎自己不超过 7.5 GB"测出来的。
  - 3060 8GB 的显存带宽是 240 GB/s，12GB 版是 360 GB/s，所以真卡上生成速度大概率比上面的数字低，具体多少没测。
  - 显示器插在这张显卡上时，Windows 桌面、浏览器等程序也要占显存。8 GB 减去引擎的 7.5 GB，只剩约 0.5 GB。如果启动失败或者特别慢，就在向导里把上下文调小一档，或者关掉占显存的程序（浏览器硬件加速、游戏等）。
  - 能用核显出画面的话（显示器插主板），独显几乎都能留给模型，也可以选 KVMem 的 48K 档。
- **只支持 RTX 30 系**：包里的程序是专门给 sm_86 编译的。
- **比 12G 版慢约 30%**，原因是 ptq1 模型本身慢。
- **一次只处理一个请求**：同时发多个会排队。
- **KVMem 输出由本轮剩余容量决定**：没有固定 16K/32K 上限；思考和正文共用这份输出预算。
- **KVMem 每轮只能看到选中的历史**：检索目标随总上下文缩放，显存紧张时还会缩小；不能保证超长内容全部召回。
- **26 万 token 第一次读入要十几分钟**：之后接着问就快了。

### 测试方法

- 速度用引擎项目自带的 `ninfer_bench`，开关某项改动交替测 3 轮。
- 显存的测法：先记下"开引擎前"的显存占用，开引擎后跑完全套测试，取过程中的最高值，两者相减就是引擎自己的占用。每个模式的上限都按"不超过 7680 MiB"一档一档试出来，测试时按 7650 卡线，留 30 MiB 误差。
- 每档都要通过：基本问答、看图、工具调用、多轮对话、项目自带的 8K 藏句找回。KVMem 模式再加 26 万 token 藏句测试。项目自带的 256K 样例在提问里就带着答案，所以换成了新的藏句内容，提问时不给提示，回答里两个值都对才算通过。
- 懒人包另外测了：向导的 9 种选法、模型转换和校验、下载和校验，以及每个引擎程序都真机启动一次，跑 `测试.bat`。

## 技术实现

下列性能数字对应原有测试，不表示每次更新都会再次获得同等提升。按日期发生的修复和发布状态见[更新记录](CHANGELOG.md)。

8G 版保留了 12G 版已有的移植和速度优化，也保留了 KVMem 与 rk8v4。视觉权重放内存和修 bug 的改动同样保留，详见[12G 技术说明](README-12GB.md#技术实现)。为了塞进 8 GB，8G 版还做了这些改动。

### 1. 换成 ptq1 模型

- 12G 版用的是 PQ2 格式（文件 7.7 GiB），8G 版换成更小的 **ptq1**（约 1.6 位，文件 6.6 GiB），文件小约 1.1 GiB，显存里的权重也相应变小。
- 3060 8GB 同样有 28 个计算单元，所以不用给它单独编译引擎。
- 我们没做 ptq1 和 PQ2 的回答质量对比。

### 2. 猜词模块（MTP）压成 Q4

- **MTP 必须留着**：关掉 MTP 只省 478 MiB，生成速度却从 45 掉到 11–12 token/秒。原因是 ptq1 一次生成一个 token 走的是没优化过的慢路径，有了 MTP 就能一次验证 4 个 token。
- 原版 MTP 是 8 位。我把其中 5 个矩阵重新量化成 4 位（Q4），**省约 210 MiB**；生成速度不变（45.2–45.6 token/秒），猜词命中率还从 62.5% 略升到 64.1%。
- MTP 只负责"猜"，每个词最后都要由主模型验证，所以它的误差**只影响猜中率，不影响回答内容**。
- 引擎改了 3 处，让它能读 Q4 格式的 MTP，原版模型的行为不变。

### 3. 词嵌入放内存

- 词嵌入就是"token 编号 → 向量"的查表，共 265 MiB。每生成一个 token 只查 1 行（约 1 KB），所以放在内存里、让显卡通过 PCIe 直接读。
- 实测速度一样（45.3 对 45.2–46.4 token/秒），猜中率完全相同。

### 4. 其他省显存的设置

- **视觉权重放内存**（和 12G 版一样）：省约 260 MiB，每张图多约 0.1 秒；
- **读入分段从 1024 改成 512**：临时缓冲区省 85 MiB，读入速度基本不变；
- **关掉额外的缓存槽**：一次只服务一个对话，用不上。

### 5. rk4v4 也能开 KVMem

- 原版引擎里 rk4v4 不让开 KVMem。查了源码，确认相关代码不区分 KV 格式，于是只放开了这个检查，没动计算代码。
- 结果：rk4v4 下显存里能放 64K（rk8v4 是 44K），所以回答空间给到 32K，历史还有 32K。26 万 token 藏句测试答对，一次写满 32K 回答也正常。
- rk8v4 和 rk4v4 的计算代码同名，没法编进同一个程序，所以包里有两个引擎程序，放在同一个文件夹，启动器按模式自动选。

### 6. 懒人包里现场转换模型

- 魔搭社区上只有原版 ptq1 模型，MTP 是 8 位的。在用户电脑上用 Python 转换得装一堆东西，所以改成打补丁。
- 补丁的原理：ptq1 原文件和 Q4 版只有 5 个 MTP 矩阵不同。补丁里记着"哪些段从原文件复制、哪些段换成新数据"，新数据只有 226 MB。
- 转换用纯 PowerShell 完成，十几秒。转完校验 SHA256，和我这边生成的文件逐字节一致后，才删掉原始文件。

### 显存账（ptq1 + Q4 MTP，视觉和词嵌入都放内存）

| 项 | 大小 |
|---|---|
| 权重 | 5.47 GiB |
| 当前对话的循环状态（48 层线性注意力） | 约 147 MiB |
| 其余临时缓冲区 | 约 205 MiB |
| KV，每 1024 token | rk8v4 27.7 MiB，rk4v4 18 MiB |
| 视觉放内存后留在显存的部分 | 约 68 MiB |
| KVMem 额外 | 约 240 MiB |

再往下省基本到头了。还能动的几项，比如输出层放内存、MTP 压到 3 位，要么会让速度掉一半，要么省得太少。

## 常见问题

- 启动失败或突然很慢：关闭其他占显存程序，在向导里把上下文或输出调小一档后重新启动。
- 主机内存分配失败：关闭其他模型，减小总上下文；16 GB 内存建议使用普通模式。
- 下载中断：重新启动，已有的下载文件会续传；校验失败时按包内说明重新下载。
- 客户端输出截断：按本次 `接入信息.txt` 填写最大输出，思考也占输出预算。
- dsh 改完不生效：退出程序和托盘图标后再打开。窗口闪退时，在包目录打开 CMD，运行 `启动.bat` 查看错误。
- DLL 加载错误：完整解压，保持引擎和依赖 DLL 在同一目录；运行库处理见[说明](CHANGELOG.md#vc-运行库或其他-dll-加载错误)。

Swift 1.5 的两项启动修复有各自适用范围，见[修复记录](CHANGELOG.md#启动错误与处理)。分享日志时请去掉 API Key 等私人信息。
