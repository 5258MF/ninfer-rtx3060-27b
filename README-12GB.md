# Bonsai2 12G 版

在 Windows 上使用 RTX 3060 12GB 运行 Swift-Bonsai-2 27B 三元模型。模型文件约 7.7 GiB，支持图片输入、工具调用和 KVMem 长对话。

## 下载与开始

下载 `ninfer-3060-12g-oneclick.zip`，网盘链接和提取码见[项目首页](README.md#下载)。现有网盘包为 2026-10-01 版；最新源码已公开，包含 2026-10-04 三项智能体兼容修改，新版网盘包待上传，差异见[更新记录](CHANGELOG.md)。

需要 RTX 30 系显卡，参数按 3060 12GB 调整。Windows 10 / 11，内存建议 32 GB，磁盘预留约 10 GB。模型不在包内，首次运行自动下载。

完整解压后双击 `启动.bat`，回车使用当前配置，按 C 打开向导；出现 `listening` 后运行 `测试.bat`，按 `接入信息.txt` 连接客户端。

## 启动与客户端

完整解压后运行 `启动.bat`；回车使用当前配置，按 C 打开向导。首次使用会下载模型。出现 `listening` 后运行 `测试.bat`。客户端按生成的 `接入信息.txt` 填写。

默认 Base URL 是 `http://127.0.0.1:8084/v1`，模型 ID 是 `qwen3.8-27b`。上下文和输出上限必须与启动配置一致。

最新源码会将较大的客户端输出上限按服务端配置封顶。KVMem 下中途压缩、编辑历史或分叉会回退到重新预填，直接续写仍可复用缓存。多工具 `required/any` 按 `Auto` 处理，不保证一定调用工具；`strict:true` 作为声明接受，不提供严格 JSON Schema 约束。接口覆盖和边界见[更新记录](CHANGELOG.md#2026-10-04三项智能体兼容修改与-bonsai2-12g-源码公开)，这些行为尚未进入现有网盘旧包。

## 模式与容量

显存只有 12 GB，所以做了四种模式，按需要选。启动时有向导，每一步都标了推荐值和上限。

| 模式 | 最长上下文 | 一次回答最多 | 适合 |
|---|---|---|---|
| **普通** | 88K（全部在显存） | 32K | 最稳，日常短对话 |
| **KVMem** | **256K** | **32K** | 长文档、长对话，速度最快 |
| **rk8v4** | 112K（全部在显存） | 32K | 超过 88K 但又希望模型直接看到全部内容 |
| **KVMem + rk8v4**（推荐） | **256K** | **32K** | 长文档、长对话、写代码的工具循环，一次还能写很长的内容 |

**推荐 KVMem + rk8v4**：默认和 KVMem 一样，上下文 256K、一次回答 32K，真实对话速度基本一样（实测 48.0 对 48.4 token/秒）。好处是同样的显存能放更多内容，需要时一次回答能开到 64K（KVMem 最多 40K）。代价是 rk8v4 格式的 PPL 多约 0.1%。

**显存上限**（2026-10-01 新版：词嵌入和视觉权重都放内存，看图照常能用）：

| 模式 | 旧版 | 新版 |
|---|---|---|
| 普通 | 65,536 | **90,112** |
| rk8v4 | 90,112 | **114,688** |
| KVMem（显存里的"检索窗口 + 回答"） | 53,248 | **77,824** |
| KVMem + rk8v4（同上） | 69,632 | **102,400** |

这些上限都是停机后一档一档实测出来的：
- 每一档都要通过文字、看图、工具调用和藏句找回测试。普通模式还要在接近上限的长文里找回藏句，KVMem 要在 26 万 token 里找回。
- 引擎不能崩，速度不能掉。
- 显示器接在这张 3060 上、桌面占约 1.3 GB 时，整卡还要剩约 200 MiB。

## 模型准备与参数调整

给同样用 RTX 30 系显卡的人：

- **只有 434 MB**。模型不在包里，第一次启动时自动从魔搭社区下载（7.7 GiB，国内直连），支持断点续传，下完自动校验。
- **不用配环境**：只要装 NVIDIA 显卡驱动 580 以上。不用装 CUDA、Python，也不用装 VC++ 运行库，需要的文件都在包里。
- **双击 `启动.bat`**：先显示上次的配置，回车直接启动；按 C 一步步重新选，一共 7 步，依次是模型、KVMem、KV 格式、看图、上下文、回答长度、思考长度。每一步都写着推荐值和上限，输入超过上限会让你重输。
- **启动后自动生成 `接入信息.txt`**：写着客户端该怎么填，包括接口地址、模型名、上下文窗口、最大输出，还有一份 DeepSeek Harness 可以直接用的配置。
- 支持 OpenAI、Anthropic Messages、OpenAI Responses 三种接口格式，支持工具调用和看图。
- **两个模型可选**：
  - **Swift-Bonsai-2**（推荐）：思考更短、出结果更快；
  - **Bonsai-2 原版**。

  本机用 AIME 20 题各跑 2 轮，Swift 37/40、原版 35/40。样本小，可以认为两者差不多。

完整测试范围见[测试结果与已知限制](#测试结果与已知限制)，内部改动见[技术实现](#技术实现)。

### 最新源码版的启动器设置

以下设置对应已公开的最新启动器，新版网盘包待上传：

| 设置 | 行为 |
|---|---|
| `KVMEM_WINDOW` / `KVRK_WINDOW` | 0 表示按空闲显存自动分配检索窗口，上限 36K |
| `KVMEM_ANSWER` / `KVRK_ANSWER` | `auto` 优先分配检索窗口，余量给输出，int8 自动最高 40K、rk8v4 自动最高 64K，至少保留 8K 输出 |
| `POST_THINKING` | 默认 1，思考结束后降低正文采样温度 |
| `RECOVER_INVARIANT` | 默认 1，对支持恢复的内部不变量错误尝试恢复 |
| 启动菜单 P / `设置显卡功耗.bat` | 可选设置显卡功耗和开机恢复；需要管理员权限，以设备支持的范围为准 |

包内 `verify-kit-manifest.ps1` 检查指定发布构建的文件、依赖和中文文件名；`verify-arch-engine.ps1` 会启动测试引擎并占用显存，运行前关闭其他模型。校验清单与内嵌哈希需随自行编译或修改脚本一起更新。

## 测试结果与已知限制

这里按版本保存已有测量和验证范围。不同工具、模型格式、提示词和输出长度的速度不能直接横向比较；文档整理没有重新测量这些历史结果。256K 是可配置的总上下文，KVMem 每轮只读入选中的历史，不能据此保证所有内容都能精确召回。

以下为 2026-10-01 及此前优化的记录，表中的“现在”对应这一发布构建。2026-10-03 第十轮结果另见[补充验证](#第十轮补充验证)。

### 速度

| 指标 | 刚部署时 | 现在 | 提升 |
|---|---|---|---|
| 实际对话生成速度（中文、英文、代码、思考 4 类平均） | 40.6 token/秒 | **52.8 token/秒** | **约 +30%** |
| 读入长文速度（2048 token 一段） | 694 token/秒 | **965 token/秒** | **+40%** |
| 短提示读入（32 token） | 218 token/秒 | **385–393 token/秒** | 约 +80% |
| 不开投机解码时的纯生成速度 | 19.6 token/秒 | **30.6–30.9 token/秒** | 约 +57% |

- 4 类内容分别是：中文 46.2、英文 50.8、代码 67.0、思考 63.1 token/秒。
- 让模型照抄一段代码或数据时，猜词命中率超过 90%，速度能到 **80–100 token/秒**。上面表格里没用这种数，按正常对话算。
- 所有数字都是同一台机器、同一个程序，打开和关闭优化交替测 3 轮，每轮之间等显卡降温，尽量排除发热降频的干扰。

### 长上下文

| 场景 | 结果 |
|---|---|
| 26 万 token 长文里藏一句话，再让它找出来 | **答对**；追问也答对，追问只要约 5 秒就开始回答 |
| 26 万 token 第一次读入 | 约 12 分钟（约 370 token/秒）；读完后生成速度仍有 51.5 token/秒 |
| 8.9 万 token 长文第一次读入 | 约 3 分钟（约 450 token/秒） |
| 6.4 万 token 文档多轮追问、追加内容再问旧内容 | 4 轮全对 |

### 正确性

- 速度优化里，**除一项以外，输出和原版逐位一致**。
- 那一项是把"什么时候切换到 int8 算法"的阈值从 33 调到 17，困惑度（PPL）只变了 +0.033%，在引擎作者给的允许范围内。
- 视觉权重放内存这个功能，看图结果和原来**逐字一致**（6 轮 18 次测试）。

### 测试环境

| 项 | 配置 |
|---|---|
| 显卡 | RTX 3060 12GB（28 SM，显存带宽 360 GB/s） |
| 内存 | 32 GB 推荐（KVMem 长对话要占约 10 GB）；16 GB 只能用普通模式 |
| 系统 | Windows 11 |
| 前端 | DeepSeek Harness 桌面版（其他 OpenAI 兼容客户端也能用） |

其他 sm_86 显卡（3060 Ti / 3070 / 3080 / 3090）用同一套源码改动就能跑，但要按实际 SM 数重新编译，各项上限也要重新测。

上面的 SM 编译说明属于已发布的 2026-10-01 版本；第十轮本机构建的变化见更新记录。

### 已知限制

- **只支持 RTX 30 系**：懒人包里的程序是专门给 sm_86 编译的，40/50 系请用原版引擎。
- **一次只处理一个请求**：同时发多个会排队。
- **KVMem 两种模式下一次回答（含思考）默认最多 32K**：超过会被截断，写长东西要分几步。可以调大，KVMem 最多 40K，KVMem + rk8v4 最多 64K（调大回答空间不会缩小检索窗口）。
- **KVMem 每轮只能看到挑出来的部分历史**：超长对话里，偶尔可能漏掉没被挑中的细节。需要模型看到全部内容时，用 rk8v4 模式（112K 以内）。
- **26 万 token 第一次读入要十几分钟**：之后接着问就很快。
- **显存余量不大**：上限是按"显示器接在这张卡上、桌面占约 1.3 GB"算的，开到上限时整卡只剩约 200 MiB。同时开着游戏、视频或浏览器硬件加速，可能变慢或起不来，这时往下调一档（4K）。显示器接在核显上就宽裕得多。

### 测试方法

- 速度测试用引擎项目自带的 `ninfer_bench`，以及真实对话的 A/B 测试脚本（中文、英文、代码、思考 4 类，采样开启）。打开和关闭优化交替测，每轮之前等显卡降到 60–65°C。
- 正确性用逐位对比输出和 PPL 门限检查，长上下文用藏句找回、多轮追问、工具循环测试。
- 每项改动都有环境变量开关，可以随时关掉，退回原版的做法。

### 第十轮补充验证

2026-10-03 的本机新构建尚待发布。这批结果与上面的历史基准分别记录：

- 固定三个提示词，temperature=0，每次输出 256 token，old / new / new / old 交替运行：旧版 54.370、新版 54.437 token/s，三个提示词的输出 hash 均相同；没有明显提速证据。
- 快速困惑度共 261167 个计分 token，新旧总体和各领域报告相同，总体 PPL 为 5.6284340215296345。
- 100K、七轮长对话在旧版、新特性关闭、512 查询、512 查询关闭 gather、1024 查询五种配置中均通过。
- 四种启动模式、看图和工具往返通过；gather 的独立逐字节校验通过。
- 完整旧 KV 单测仍有 3 项预留/驻留语义断言失败，相关预留函数与本轮前相同；未把完整单测列为通过。

## 技术实现

下列性能数字对应原有测试，不表示每次更新都会再次获得同等提升。按日期发生的修复和发布状态见[更新记录](CHANGELOG.md)。

### 1. 让引擎能在 RTX 30 系上跑

原版引擎只支持 RTX 40/50 系（sm_89 / sm_120），在 3060 上编译不过、跑不起来。移植时改了这些：
- 编译配置里放行 sm_86；
- 3060 只有 28 个计算单元（SM），而原版按 82 个设计，改掉后才不会一启动就报错；
- 3060 不支持 FP8 指令，把这条路径关掉；

### 2. 生成速度优化（+27~30%）

- **单 token 生成改走 Tensor Core**：原来用的是逐行的普通计算。
- **2-bit 权重改成在寄存器里直接解码**：原来要查一张放在共享内存里的表，访问冲突严重，带宽卡在理论值的一半左右。改完带宽提升 20–50%，输出逐位一致。
- **只搬实际需要的数据行**：每个计算单元能同时多跑一两组任务，又快了 3–14%。

### 3. 读入速度优化（+40%）

- **自己写了一个新的 int8 计算核心**（提升最大的一项）：
  - 权重在寄存器里解码，省掉一轮来回搬运；
  - 计算块加大到 32×64；
  - 三级流水线；
  - 按显卡二级缓存（L2）的大小分组调度，让权重和输入尽量留在缓存里；
  - 输出先在共享内存里整理，再合并写回显存。

  效果：矩阵计算从 45 TOPS 提到 61 TOPS，整体读入快了 26–27%，**输出逐位一致**。
- **输入量化改成向量化读写**：从 40.7 ms 降到 22.8 ms，已经接近显存带宽的极限。
- **任务网格化**：让 28 个计算单元都有活干。
- **重新标定切换阈值**：实测 3060 上的最佳切换点是 17 个 token，和引擎作者在另一张卡上的结论一致。

一些方案经测试没有收益，未纳入当时的发布构建。

### 4. KVMem：12 GB 显存跑 256K 上下文

参考 kvmem-llama.cpp 的做法和官方推荐参数，移植到这个引擎上：
- **显存里只放活动窗口**：开头 8K 的系统提示和工具定义，加上按当前问题挑出的历史，以及回答预留空间；窗口大小取决于模式和配置，见[12G 使用指南](#模式与容量)；
- **其余历史放在普通内存里**：256K 大约要 8.4 GiB，用的是普通可换页内存，不锁页，没有锁页内存不够用的问题；
- **和投机解码（MTP）兼容**：最早的版本开 KVMem 必须关 MTP，速度从 53 掉到 30。现在 KVMem 下真实对话仍有 **48–50 token/秒**。

之后又对照 KVMem 的论文迭代了几版：
- 挑历史时用**用户真正的问题**，不只用工具返回的结果。以前在 8.9 万 token 的工具结果场景里会答错，现在答对了；
- 本轮新输入的内容一定保留在显存里；
- 历史被挤出显存后，按新挑出来的内容把本轮输入重新算一遍，和论文的做法一致。

### 5. rk8v4：更省显存的 KV 格式

- 对话记录（KV）里，K 部分用 int8，V 部分用 4-bit，每个 token 只占 int8 格式的 77%；
- 同样的显存，上下文多放约 30%（普通 88K → rk8v4 112K）；
- 代价是 PPL 增加约 0.1%，短对话时生成慢约 5%；
- 8.6 万 token 的藏句测试 3 次全对。

### 6. 视觉权重和词嵌入放内存

- 看图功能本来要常驻约 300 MiB 显存。现在平时放在内存里，来图时分 30 段依次搬上显卡计算，每张图多约 0.1 秒。
- 词嵌入表（把文字变成向量的那张表）占 322 MiB。现在也放在内存里，每步只读用到的那几行，显卡直接从内存读。
- 两项合计省下约 600 MiB 显存，每种模式的上限都高了 2～4 档。读入和生成速度不变，看图结果和原来逐字一致。
- 2026-10-01 的 12G 发布版未采用 8G 方案中的“MTP 压成 4-bit”和“读入分段 512”，对应当时的测试结果：
  - MTP 压成 4-bit：猜中率从 0.679 降到 0.655，生成慢约 3%；
  - 读入分段 512：当时读入慢约 2%，省的显存不够多开一档；2026-10-03 的本机第十轮构建按本轮目标统一使用 512。


## 源码与编译

完整源码在 [`bonsai2-12g/engine/`](bonsai2-12g/engine/)，启动器、公开默认设置、测试与功耗工具在 [`oneclick/`](bonsai2-12g/oneclick/)，构建入口为 [`build-sm86.bat`](bonsai2-12g/scripts/build-sm86.bat)。目录索引见 [bonsai2-12g/README.md](bonsai2-12g/README.md)。

Windows 构建需要 CUDA 13.1 以上（现有构建使用 13.3）、MSVC C++ 工具链、CMake 3.28 以上和 Ninja。看图构建还需 FFmpeg 开发包，将 `include` 和 `lib` 放入 `bonsai2-12g/engine/ffmpeg/`；该目录和运行时 DLL 由使用者准备，不随源码提交。

在仓库根目录运行：

```bat
set "NINFER_CUDA_PATH=C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.3"
set "NINFER_VCVARS64=C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"
bonsai2-12g\scripts\build-sm86.bat
```

脚本按仓库相对路径定位源码，输出到 `bonsai2-12g/build/`，默认构建 sm_86 的 `apps/ninfer-serve.exe` 和 `apps/ninfer-perplexity.exe`。按安装位置设置工具链路径；CMake 和 Ninja 需在 PATH 中，也可用 `NINFER_TOOLS_PATH` 指定它们的目录（多个目录用分号分隔）。源码和构建目录使用纯英文路径。完成后将程序及相应运行时 DLL 放入懒人包的 `engine` 目录，已有模型继续使用。

已有构建只需运行 `build-sm86.bat build`；`configure` 仅生成构建。若只编译文字服务，可设置 `NINFER_DISABLE_MEDIA=ON`；这样不提供图片/视频解码。测试和基准默认关闭，可以通过 `NINFER_BUILD_TESTING=ON`、`NINFER_BUILD_BENCHMARKS=ON` 配置，再构建相应目标。完整旧 KV 单测的三项历史断言失败仍需按上方说明解读。

引擎数学实现、模型绑定、KVMem、工具和依赖源码均在仓库中；模型、编译产物、运行记录及个人配置不属于源码目录。三项修改的发布状态和接口限制见 [CHANGELOG](CHANGELOG.md#2026-10-04三项智能体兼容修改与-bonsai2-12g-源码公开)。

## 常见问题

- 启动失败或突然很慢：关闭其他占显存程序，在向导里把上下文或输出调小一档后重新启动。
- 主机内存分配失败：关闭其他模型，减小总上下文；16 GB 内存建议使用普通模式。
- 下载中断：重新启动，已有的下载文件会续传；校验失败时按包内说明重新下载。
- 客户端输出截断：按本次 `接入信息.txt` 填写最大输出，思考也占输出预算。
- dsh 改完不生效：退出程序和托盘图标后再打开。窗口闪退时，在包目录打开 CMD，运行 `启动.bat` 查看错误。
- DLL 加载错误：完整解压，保持引擎和依赖 DLL 在同一目录；运行库处理见[说明](CHANGELOG.md#vc-运行库或其他-dll-加载错误)。

Swift 1.5 的两项启动修复有各自适用范围，见[修复记录](CHANGELOG.md#启动错误与处理)。分享日志时请去掉 API Key 等私人信息。
